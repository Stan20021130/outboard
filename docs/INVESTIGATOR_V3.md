# Investigator v0.3：优化与 DSH 复测

日期：2026-11-03（Asia/Shanghai）。

v0.3 在本轮任务集上减少了总 Token，但没有实现“更省且更快”：8 次真实 DSH 运行中，原生执行与卸载均为 4/4 成功；卸载平均总 Token 减少 **13.8%**，主 Agent 自身 Token 减少 **31.5%**，主任务完整执行时间增加 **45.3%**。实际金额节省尚未建立，缓存与输出构成需要分别计价。

## 实现变化

- 按问题中的标识符选择可执行代码窗口和短测试体，跳过长文档。初始片段最多 260 行、16000 字符，取消旧版影响上下文和通用预取的重复注入。
- 接受 `Context.__init__` 一类限定名称。专用符号工具返回方法位置、函数体及有界词法引用；批量读取自动分段，每段请求最多 300 行、整批最多 400 行，内部引用仍不超过 100 行。
- Runtime 给已观察片段分配证据 ID，模型选择 ID，Runtime 回填原文和行号。重叠读取复用已交付片段，减少抄写错误和重复输入。
- 最多两轮集中补证据，随后汇总和独立复核。剩余缺口必须保留为 `partial`。这是一项有界策略，不能仅凭更早停止就宣称效率提高。
- MCP `investigate_repository` 使用 `format_version=2`：引用集中在顶层 `evidence` 表中，条目只引用 ID。CLI 和内部 Python 结果仍展开引用。调用 Skill 说明了静态验收边界，以及将同一目标的定位与影响调查合并调用。

原文校验、验收覆盖、相同模型的独立语义复核、仓库状态检查和预算限制保留。独立复核可以在发现一项实质性不支持时立即拒绝；批准仍要求全部断言得到支持。本轮没有降低最终测试要求或更换廉价模型。

## 实验设置

- 宿主：DSH `0.2.1-rc.5`，两组均使用 `deepseek-v4.1-flash`、`reasoning=low`。
- A：主 Agent 使用原生工具直接完成。B：同一主 Agent 必须调用专用 Investigator，再完成修复和测试。没有普通 Subagent 组。
- 仓库：Click，提交 `2247b35ea1c47c727d7a06e51fa280e12a863ff6`。每次在独立、非空副本中开始。
- 任务一：既有的连字符 `auto_envvar_prefix` 回归。任务二：运行时冻结后准备的 `default_map=None` 参数来源回归，涉及嵌套默认值、可调用默认值与 CLI／环境变量优先级。
- 每个任务两组配对，轮换执行顺序，共 8 次；任务、变异、隐藏验收、预算及驱动哈希在本轮正式执行前冻结。
- 成功必须保留原测试语句与配置，并通过原始非压力测试及不提供给模型的隐藏验收。新增测试使用原测试与候选生产代码的独立副本统一验收，不通过修改原有测试获得成功。
- 主任务预算 300 秒、500000 Token；单次 Subagent 预算 150 秒、200000 Token。协调、失败调用、重试和独立复核均计入；全部 8 次均未超过主任务 Token 预算。
- 两组均为相同本地权限，源码副本不是 OS 沙箱；没有开放原生额外委派。

DSH 使用与旧实验相同的冻结调用指导，未加载本项目最新 Skill。因此新 Skill 关于合并调用的文字调整没有被当作本轮实测收益。

## Token 减少不等于金额减少

下表是每组四次运行合计，包含主 Agent 和 Subagent。缓存输入已经包含在总输入中，不能再额外相加。

| 执行方式 | 缓存输入 | 未缓存输入 | 输出（含推理） | 总 Token |
| --- | ---: | ---: | ---: | ---: |
| 原生 | 1,320,448 | 84,749 | 26,253 | 1,431,450 |
| 卸载 | 909,824 | 253,512 | 71,039 | 1,234,375 |

卸载减少了缓存输入，同时增加了未缓存输入和输出。设每百万未缓存输入、缓存输入、输出的单价分别为 `p_in`、`p_cached`、`p_out`，本轮四次卸载相对四次原生的金额差为：

```text
Cost_B − Cost_A = 0.168763 × p_in − 0.410624 × p_cached + 0.044786 × p_out
```

当前代理没有提供这三项实际单价，因此不能报告金额节省，也不能把 13.8% 的 Token 下降换算为 13.8% 的账单下降。

## 轨迹解释

原生共有 70 次模型请求。卸载组主 Agent 降到 54 次，新增 21 次子模型请求，总数为 75 次。主 Agent 的部分工作确实被移走了，但新增执行和审核仍增加了串行调用。

四个卸载任务共尝试 6 次调查调用：2 次 `completed`，3 次 `partial`，1 次在模型调用前因无效 Patch 失败。`partial` 没有被计为调查完成，主 Agent 的继续调查与修复仍计入总账。全部最终任务成功并不证明这些子任务本身已经达到统计意义上的同等质量。

日志可见的额外开销包括：卸载前已读取关键实现；对同一目标先定位再调用影响调查；无效 Patch 导致重试；复核指出缺少测试或调用链证据后，主 Agent 继续调查。最新 Skill 对合并调用和使用实际 Diff 作了说明，但该指导的独立效果还未评估。

新场景的子模型两次分别使用 52682、45287 Token；第二次返回 `completed` 并通过独立复核。原场景一次为一项缺口返回 `partial`，另一次发生多次调用。收益明显依赖调用目标和任务边界，不能推广为所有代码探索都应该卸载。

上述观察没有做逐项消融。上下文编译、证据 ID、调用预算与主 Agent 行为的独立贡献，不能由这 8 次运行分别确定。

## 开发重放与历史参考

旧版源码在修改前归档。使用未改动的旧任务 Capsule 重放时，同一份包含“Existing tests pass”的输入：v0.2 为 177385 Token、54.02 秒，因引用错误未进入语义复核；v0.3 为 44490 Token、66.45 秒，引用结构有效，但语义复核拒绝过度结论。两边都为 `partial`。它说明 Token 开销改善，不证明该子任务已完成，也不替代原生主 Agent 对照。

原场景历史 v0.2 卸载平均为 393690 Token，本轮 v0.3 为 305935.5，下降约 22.3%；子模型从约 159603.5 降到 78274 Token，约减半。但历史平均主任务时间 194.41 秒，本轮 210.77 秒。历史对比不是同期配对，不能将全部差异归因于新实现。旧实验原始数据和负面结论仍保留。

## 校验、限制与复核

- 发布验证的 52 项测试全部通过（`python -m unittest discover -s tests -v`）；日志见下方。Skill 的 `quick_validate.py` 检查通过。
- DSH 主 Agent 用量与透明 HTTP 账本按主角色核对；Subagent SDK 日志与子角色账本单独核对，全部一致。模型、推理配置、快照不变、Patch 可应用性、预算和冻结驱动检查均通过。
- 初版 v0.3 汇总辅助函数曾把 DSH 的主 Agent 用量与主子合计相比，导致错误的“不一致”标志。该初版保存在 `preliminary-summary.json`；正式报告使用 `dsh_report.py` 按角色核对，并修复多个任务同属 impact 场景时的聚合覆盖问题。没有因此重跑模型、删除样本或改变原始运行。
- 正式执行所用后端指纹为 `8fa9b69a64e240e0dad744a2447f632bbe5f68f14fd79a338b5e38bb617afac1`。发布前仅将 `__init__.__version__` 从 0.2.0 对齐为 0.3.0；源码差异检查确认除此之外与归档相同，发布指纹记录在 final-audit 中。
- 首个原场景 A 运行与本项目单测末段短暂重叠。整轮没有隔离机器负载、OS 缓存或提供方缓存，时延只作探索性观察；两个新场景配对没有这项单测重叠。
- 只有一个仓库、两个受控变异，每个两次配对；不等同于真实历史 Issue 随机样本，也不能建立质量非劣结论。主 Agent 均从新会话开始，未覆盖长历史任务。
- B 被要求调用工具，这是受控卸载机制实验，不是自主选择策略的收益证明。
