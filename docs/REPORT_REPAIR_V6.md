# v0.6：定位交接开销，只复测卸载组

日期：2026-11-03（Asia/Shanghai）。

本轮按用户要求只重新执行特调 Subagent 卸载组。v0.5 的四次原生执行和四次卸载运行均原样保留，作为历史参照，不重新启动原生 Agent。两条任务、源码快照、任务简报、模型和预算不变；最终仍运行原始完整非压力测试和隐藏验收。

## 定位到的问题

v0.5 调查共进行了八次报告尝试，却只交接四份报告。触发额外调用的具体错误包括：

- 把多个公共接口事实塞进一个 finding，引用达到七条，超过六条上限。
- 在 `criteria_coverage` 中多生成了空的 `evidence: []`。
- 将覆盖状态写成契约之外的值。
- 相关测试的文件路径与其证据所在文件不一致。

原循环要求模型重写整份报告，已经正确的结论、测试和覆盖映射也被重新生成。这增加输出、下一轮输入和事实漂移机会。

另外，搜索工具只有命中行，不支持限定生产代码／测试路径。测试参数表与断言往往不在命中行，模型在两轮取证后仍缺少测试行为证据。报告中的 `partial` 因而不只是格式问题，不能用放宽引用校验或更改状态掩盖。

宿主集成也有两项额外开销：旧的通用评测指导要求只读调查前先查询快照，而调查器本来就会自行捕获并返回快照；部分主 Agent 则在新增测试之前先跑完整套件，随后再次完整回归。

## 改动

1. 新增内部 `amend_investigation`。报告校验失败后，模型返回针对字段的 JSON Pointer 修改，程序以原草稿为基础原子应用，再重新校验整份报告。工具参数不能修改源码、权限、预算或运行状态。未知证据、越界引用、无效覆盖映射和变化的快照仍不能通过。
2. 程序只自动移除覆盖条目中多余的空 `evidence: []`。非空额外证据继续报错，不静默丢弃结论或引用。不删除验收问题，不缩短已有事实或原文来伪造成功。
3. 调查策略改用短的原子事实，避免把几个结论挤进一条 finding；显式提醒引用数量、合法状态和测试路径约束。相关测试恢复到公开契约已有的十条上限，避免原有四条内部限制挤掉题目点名的行为。
4. 新增内部 `find_tests`：基于 AST 一次检索并读取测试参数化装饰器与函数体，返回候选位置索引。每次最多 400 行、16000 字节，每段最多 100 行，截断会明确标记，所有返回原文都纳入已观察证据记录。搜索也可限制在任务范围内的文件／目录前缀。
5. 调用 Skill、MCP 工具说明指导主 Agent 直接发起只读调查，先完成代码和新增测试，用聚焦检查迭代，再对最终工作区执行必需的完整验证。已通过结果只在相关输入与环境未变化时可复用；变化后仍需验证。DSH 的只读场景移除了多余快照握手及无关执行检查指导。
6. 首轮完整复测暴露出主 Agent 猜测了其他包的路径、漏传变更锚点的问题。工具发现阶段现在附带 `pyproject.toml` 的包名标签，并明确 `change_impact` 的条件必填项。包名读取有大小限制，跳过链接／重解析点、校验路径边界，且只接受受限 ASCII 标签；不把原始元数据作为指令或源码证明。没有有效标签时照常工作。提前失败的运行也初始化零取证轮次，避免报告器漏掉此类失败。

公开 MCP 结果继续为 `format_version=3`。底层模型仍为 `deepseek-v4.1-flash`，推理配置仍为 `low`，不增加独立 LLM 审稿。稳定工具 Schema 保留，局部修补工具从首轮起即在列表中；强制工具选择随报告状态变化，工具定义不变化。

## 改善来自哪里，剩余开销是什么

最终轮子 Agent 进行了八次取证、四次整份报告提交及两次局部修补。两次局部修补合计 611 输出 Token；v0.5 则是八次整份报告提交。整份报告加修补的输出从 19056 降至 12684 Token，相关 API 请求时间从 86.484 降至 66.907 秒。对未编辑字段的保留是程序保证，修改后的整份报告仍经原校验流程，不以少验证字段换取速度。

最终子任务平均耗时 28.367 秒（v0.5 为 32.621），主 Agent 的平均输出从 5802.50 降至 4303.75 Token，子 Agent 从 5288.00 降至 3763.75。收益包括更完整的测试取证、较少整份报告重写及较少主 Agent 后续轮次，不能全部归因于单个开关或缓存。

最终四份调查是一份完整、三份部分完成，模型声明的完成数量与历史 v0.5 相同；部分完成报告没有伪装成成功调查。主 Agent 仍处理缺口并完成代码和测试。程序化引用检查不等于独立语义认证，不据这四份报告宣称自然语言结论质量已经统计非劣。

原生／v0.5 卸载／v0.6 卸载的完整 pytest 调用分别为 4／6／5 次。最终仍有一个样本先跑完整套件，再添加测试后重跑。四个最终样本都在最后一次源码／测试修改之后通过完整套件，再通过原始测试与隐藏 oracle 的外部验收，记录于 `workflow-audit.json`。没有通过少跑必需验证取得收益。

相对历史原生，最终卸载平均多约 26.848 秒；API 请求总时间多约 7.727 秒，pytest 自报时间多约 8.028 秒，其余约 11.093 秒包含启动、工具、上下文构造与协调的净差异。没有采集纯输出生成时间，不能把整个差异归因于输出 Token。子 Agent 初次报告本身仍占其输出约八成，主 Agent 仍要继续分析和修改，这部分交接开销尚未消除。

## 复现与核账

```powershell
uv run python -X utf8 benchmarks/dsh_report_repair.py prepare
uv run python -X utf8 benchmarks/dsh_report_repair.py probe
uv run python -X utf8 benchmarks/dsh_report_repair.py freeze
uv run python -X utf8 benchmarks/dsh_report_repair.py run
uv run python -X utf8 benchmarks/dsh_report_repair.py report
# 最终轮：同样只允许 offload
uv run python -X utf8 benchmarks/dsh_repository_handoff.py freeze
uv run python -X utf8 benchmarks/dsh_repository_handoff.py run
uv run python -X utf8 benchmarks/dsh_repository_handoff.py report
uv run python -X utf8 benchmarks/dsh_projection_audit.py .trajectory/report-repair-optimization/dsh-v6-final
```

驱动拒绝任何 `arm != offload` 的调度。原始材料位于 `.trajectory/report-repair-optimization/`，按源码指纹区分回放；首轮完整运行位于 `dsh-v6/runs`，最终轮位于 `dsh-v6-final/runs`。结果、外部验收和用量为 `summary.json`、`analysis.json`，与历史组的比较为 `comparison.json`。

DSH headless 的 JSON 事件投影默认把字符串限制为 8192 UTF-8 字节，大报告的日志预览因此不一定是完整 JSON。核对了本机 `dsh-headless` 与 MCP 适配器实现，未把预览截断推断成模型收到的内容截断。`projection-audit.json` 将预览与 FastMCP 序列化的完整 worker 结果逐项匹配，并单独计入无 worker 的输入拒绝。首轮与最终轮都能完整对账；不改写日志、不丢弃失败成本。早期直接解析预览的 `handoff-audit.json` 保留了这种解析失败，最终调用核对以补充投影审计为准。

最终主／子用量、模型与推理配置均核账一致，四个 worker 每轮工具 Schema 保持一致、取证不超过两轮、源码快照不变；四份补丁均可应用，原始测试和配置保留，未以同名测试覆盖原断言。每个最终样本都有真实模型执行的调查，不是只发出一次无效 MCP 调用再由主 Agent 独自完成。

最终源码通过完整测试套件 74 项。调用 Skill 通过 quick_validate。最终模型运行的功能验收、预算与保护核账另列，不能用单元测试代替真实结果。

比较 v0.5 卸载和历史原生时使用相同任务／重复编号，但不是同期重新随机执行的 A/B；缓存、API 负载及模型随机性可能影响数值。没有真实分项价格时，不把总 Token 变化换算成账单节省，也不据四次运行宣称统计质量非劣。
